# ADR-0001 —— 确立核心工程原则为最高准则

- **状态**：采纳
- **日期**：2026-09-24

## 背景

WebReader 已有详尽的项目特化规则（`AGENTS.md` 的分层契约 / 验证要求 / Git 工作流，
`RULES.md` 的代码地图），但缺少**跨项目的通用工程准则**来回答这类问题：

- 动手前要不要先设计，还是先实现再说？
- 文件多大算太大、模块边界怎么定？
- 老代码与新设计冲突时，该兼容还是该删？
- 什么样的 TODO / 注释算「有上下文」？
- 什么时候该抽象、什么时候该重复？

缺少这些准则时，每个改动只能凭当下的判断，长期会朝着「实现便利优先」漂移：
文件膨胀、兼容层堆积、决策原因丢失。本 ADR 把一组通用工程原则确立为仓库的
**最高准则**，让上述问题有确定的判据。

## 决策

采纳下列十条原则（编号沿用来源，缺第 4 / 5 项）作为 WebReader 的**最高工程准则**，
优先级高于 `AGENTS.md` 其余各节及所有其他文档；原文见 `AGENTS.md` §0.1：

1. 架构与领域优先（不做推测性抽象，抽象延迟到第二个真实用例）
2. 追求优雅的代码模块（**单文件 ≤ 500 行**）
3. 保持边界与数据流清晰（协议 / 领域 / 持久化 / 视图模型不互相泄漏）
6. 保障完整前端体验（加载 / 空状态 / 错误 / 重试 / 反馈 / 可访问性）
7. 复用稳定的业务语义（先核查已有依赖，不过早抽象）
8. 为未来维护者保留上下文（ADR + 技术债务登记表，禁止无上下文 TODO）
9. 确保变更可验证、可观测、可回滚（日志保留诊断上下文但不泄露敏感信息）
10. 删除优于兼容（内部重构直接删除；对外契约按合同义务评估）

### 落地方式

- `AGENTS.md` §0.2 给出每条原则在本项目中的**具体执行方式与四类模型映射表**；
- `AGENTS.md` §1.2 把契约冻结点分级为【对外】（合同义务）与【内部】（删除优先），
  让原则十在扩展项目中可执行而非空喊；
- `AGENTS.md` §3 / §5 / §6 把原则变成**验证闸门与完成定义检查项**；
- 现有与原则不符的存量（8 个超 500 行的文件等）**登记在 `docs/tech-debt.md`**，
  按登记顺序逐步清理，而不是假装合规。

## 结果

- **正面影响**：新改动有一致的判据；模块边界与文件规模有可量化标准；
  决策与债务可追踪，不依赖个人记忆；`AGENTS.md` 的其余规则被收窄为「项目特化」内容，
  职责更清晰。
- **代价 / 风险**：
  - 存量代码暂时不合规（见 `docs/tech-debt.md`），需要时间清理；清理涉及
    popup / content 界面层时按 `AGENTS.md` §3 走浏览器手动回归，成本不低；
  - 「500 行」是硬阈值而非目标值——接近 400 行就应规划拆分，否则容易为了卡线
    而做勉强的拆分（反而破坏内聚）；
  - 原则十（删除优于兼容）与「老用户数据兼容」存在表面张力：靠 §1.2 的
    【对外】/【内部】分级消解，分级错误会造成误删，改分级时必须复核调用方。
- **触发重评估的条件**：
  - 若 500 行上限持续导致高内聚模块被强行拆碎（出现大量 3–5 行的转发文件），
    应重评该阈值；
  - 若项目新增 `packages/` workspace 或第二个上游 TTS 引擎（真实用例），
    原则 1 的抽象策略与 §0.2 的模型映射需相应更新。
