# ADR-0002 —— 默认音色按界面语言派生，取消正文语言自动检测

- **状态**：采纳
- **日期**：2026-09-26

## 背景

原设计用「自动检测语言」开关（`autoDetectLanguage`，默认开）驱动音色选择：
朗读前对正文做词频加权 + 字符脚本检测（`shared/detect-language/`，七个文件、
上千行词表），按检测结果匹配音色并写入 `state.selectedVoice`。该方案有三个问题：

1. **误判体感差**：中英混排、短文本、拉丁语种常被误判（小语种词频得分高时平局
   规则也未必兜得住），命中无可用音色的语种时静默回退 `mimo_default`，用户不知情；
2. **状态机脆弱**：「自动检测 / 手选」是互斥关系，两层各有恢复分支与回退兜底，
   popup 层存在同源缺陷（清除后未重开自动检测则
   播放报「请选择音色」）；
3. **死重逻辑**：MiMo 预置音色只有中英两语种，而界面语言本身就只有中 / 英两档，
   检测出的绝大多数语种最终都回退到默认音色——检测的实际收益极低。

## 决策

**默认音色完全由用户当前选择的界面语言决定，正文不参与音色选择。**

- 新增纯领域模块 `shared/voice-default.ts`：`pickDefaultVoice(voices, locale)`
  把界面语言映射到音色主语言前缀（`zh_CN → zh`、`en → en`，未知回退 `en`），
  取目录中首个匹配音色；无匹配语种时回退 `mimo_default`（双语兜底），仍无则
  回退目录首个音色
- `state.selectedVoice` 保持「当前要使用的音色」的**单一来源**不变，新增
  `state.voiceSelectionIsManual` 区分来源：
  - `true` → 用户手选，按 name 持久化到 `selectedVoice`，**界面语言切换不覆盖**
  - `false` → 派生的默认音色，**不落盘**，随界面语言变化重新派生
- 存储键 `selectedVoice` 语义从「自动检测时为 null」改为「null = 跟随界面语言」。
  老用户数据自动兼容：存了名字的按手选恢复；存 null 的改为按界面语言派生
- 删除 `autoDetectLanguage` 开关与其全部调用点；删除零引用的
  `shared/detect-language/` 与其行为锁定测试
- **本地容灾**（`speechSynthesis`）的语言改用所选音色的 `voice.language`：
  语言完全由音色决定，链路中不再有任何检测

## 结果

- **正面影响**：
  - 中 / 英界面用户的默认音色稳定可预期，切换界面语言即切换默认音色（未手选时）
  - 消除 TD-011 的互斥状态机缺陷：单一来源 + 一个布尔标记，两层恢复逻辑收敛为
    「手选在列表内则恢复，否则派生」
  - 删除约 1600 行检测死代码与其测试，`content/player` 不再依赖检测结果
- **代价 / 风险**：
  - **行为变化**：原开启自动检测的用户，不再按正文逐句切换音色（中英混排网页
    会用同一个音色读到底）。这是需求预期的取舍，已在发布说明登记
  - **本地容灾取舍**：选了中文音色读英文文本时，本地音色也用中文语种朗读。
    理由是语言由用户选定的音色唯一决定，避免「界面一个语言、播放另一个语言」
    的不自洽
  - 存储中残留的 `autoDetectLanguage` 布尔成为孤儿键（只留不读），良性
- **触发重评估的条件**：
  - 音色目录扩展到多语种（如 relay 后端提供十几种语言），且用户明显需要
    「读什么语言就用什么音色」时——届时应重新引入检测，或改为按段落动态切换
  - 出现「界面语言与正文语言常态不一致」的强诉求
