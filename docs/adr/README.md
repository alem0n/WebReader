# ADR — 架构决策记录

WebReader 的**关键架构决策**记录在此（`AGENTS.md` §0 原则八要求）。

## 为什么写 ADR

代码、注释和架构文档是跨越时间的协作媒介。非显然的设计决策只留在脑子里或聊天记录里，
下一位维护者就会重新踩一遍坑。ADR 让每个关键决策**自带上下文**：为什么这么定、
代价是什么、什么条件下会推翻。

## 格式

文件名 `NNNN-kebab-case-title.md`，编号从 `0001` 连续不跳号。内容结构：

```markdown
# ADR-NNNN —— 标题

- **状态**：采纳 / 提案 / 已废弃（废弃须注明被哪个 ADR 取代）
- **日期**：YYYY-MM-DD

## 背景
为什么需要这个决策；当时的约束、备选方案。

## 决策
最终定了什么。

## 结果
- 正面影响：
- 代价 / 风险：
- 触发重评估的条件（什么情况下应该推翻本决策）：

## 反向链接
关联的 `AGENTS.md` 章节、`docs/tech-debt.md` 条目、相关模块。
```

## 与其他文档的关系

- **优先级低于 `AGENTS.md` §0**：ADR 记录的是「在 §0 约束下、针对本项目的具体取舍」，
  不得与 §0 冲突；冲突时以 §0 为准；
- **不是教程**：怎么用 / 功能事实看 `README.md`，代码地图看 `RULES.md`；
- **技术债务另放**：已知缺陷 / 临时方案 / 待清理项登记在 `docs/tech-debt.md`，
  ADR 只记「为什么这样设计」，不记「什么时候还债」。
